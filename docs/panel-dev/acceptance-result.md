## 四、一处**如实说明**的观察（不是缺陷）

刚添加完时，该账号额度显示为 `—`（未知）：

```
新增后立即查:  示例昵称  aaaaaaaa…  正常  —  (未知)
执行 status 后: 示例昵称  aaaaaaaa…  正常  2xxx
```

**【实测】执行一次 `wbapi status`（即刷新额度）后即有值，与删除前一致。**

⇒ 原因：**刚添加的账号还没有额度快照**，需刷新一次才显示。
这属于**显示时机**问题，不是数据错误。
（面板上刷新一次即可；若要改进，可在登录落盘后自动查一次额度 —— 见下方"后续可选"。）

### 后续可选改进（**已排查，结论如下**）

**现象**：登录落盘后该账号额度显示 `—`（未知），执行一次 `status` 后变为具体数值。

**排查过程（不是猜，是读代码确认的）**：

1. `runLogin` 的顺序**正确**：先 `Accounts.Put(acct)`（约 194 行），
   再 `Accounts.Mutate(uid, …)` 写额度快照（约 201 行），
   且 `Mutate` 对已存在的 uid 能正常工作 ⇒ **不是顺序/竞态问题**。
2. `Mutate` 块被 `if credits != nil` 包着 ⇒ 说明**当时 `credits` 确实是 nil**。
3. 在 `verifyCredential` → `Credit` 这条路径上，`credits` 为 nil 对应
   上游 `get-user-resource` 返回的 **`Accounts` 数组为空**
   （`checkin.go`: `if len(accts) > 0 { out.Remaining = &t }`）。
4. 而**同一账号**随后 `status` 查询返回 **2891** ⇒
   当次额度响应**是空的**。

⚠️ **措辞纪律（Codex 第 35 轮纠正）**：
第 3 点**不能**说成"唯一条件" —— 那需要先**穷举 `Credit` 的所有错误、
业务码与解析分支**才能这样表述。当前只能说
**"最合理的解释是当次上游响应为空"**。

**结论**：最合理的解释是**上游瞬时返回空额度列表**，属**外部行为**，
不是本项目的逻辑缺陷 —— 但**会**让刚添加的账号短暂显示 `—`。

### 发布说明措辞（Codex 给定，照此表述）

> 曾观察到登录后额度暂时未知，随后状态查询恢复；
> **发生频率和触发条件尚未确定**。

⚠️ **不要**写成"额度丢失"或"已知必现缺陷"。

### 处理决定（Codex 第 35 轮裁定）

- **暂不加自动重查**：「没有频率和因果证据时，不应为了修一次观察到的空响应
  增加延迟或重复请求。」
- 替代做法：**保留手动状态刷新**；后续**收集样本**后再决定是否加一次**有限重试**。
- 属**发布说明内容**，但**不是发布阻塞**。

**本轮未做任何代码改动。**
