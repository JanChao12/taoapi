# 网页登录页行为实测定位（含一条**重要更正**）

> **2026-10-05 实测**。起因：refresh 续期实验第 1 步（真实登录捕获凭据）时，
> 委托方连续多次报告页面拒绝登录，我据此做了 CDP 抓包与存储对比定位。
>
> **本文全部是实测证据**（CDP 抓到的真实请求/响应 + 页面截图 + 存储长度对比），
> 不是推断。推断部分会显式标注。

---

## 零、⭐ 最重要的结论（委托方先发现的）

> **委托方原话**：「我怀疑这里每次都报错，但是实际可能是已经登录成功了」

**这个判断经实测证实是对的。**

页面显示的

```
登录失败
请返回客户端点击「重新发起登录」重试
问题标识：<每次不同的 UUID>
```

**不是认证失败**，而是「**没有客户端来取凭据**」的兜底文案。
判定依据（三条独立证据，见第二节）：

1. 登录后**所有**初始化接口都返回 `code:0` / HTTP 200 —— **没有一个失败**
2. 登录成功后浏览器存储里的凭据项**长度显著增长**（414→1240、234→700 字节）
3. 抓包里 **`/console/login/enterprise` 根本没被调用** ——
   页面并没有走到"下发凭据"那一步，因为**不知道下发给谁**

⇒ 这是"**凭据已备好、无人认领**"的状态。对我们反而是**好消息**：
说明上游确实按 `state` 暂存凭据，等客户端来取 —— 正是设计所依赖的机制。

## 一、现象与**我的两次误判**（都要记下来）

### 误判 ①：以为"页面一加载就判定失败、根本没进登录流程"

**实际**：页面确实进了登录流程。第一次停在**「选择账号」**
（因为已有登录态），再点「切换登录用户」后**正经渲染出了登录表单**
（手机验证码登录 / 微信 / 邮箱 / SSO）。

**教训**：只凭"页面可见文本里有失败字样"就下结论是错的 ——
**必须同时确认该文本出现的时机**（加载即出现？还是某步操作之后？）。

### 误判 ②：以为"profile 里有上次残留的旧 token"

**实际**：profile 是 `os.MkdirTemp` 本次**新建**的
（创建时间 22:55:19 与本次启动一致，见原第六节）。

**教训**：判断"是否残留"要看文件的**创建时间**，不能只看"文件存在"。
另外**同一个失败文案在不同阶段出现，原因可以完全不同**
（加载即失败 vs 登录后备好凭据），不能混为一谈。

## 二、实测证据

### 2.1 页面初始化请求序列（CDP 抓包，真实）

```
GET  /v2/plugin/login/gray-decision?feature=oneid_component&platform=CLI  → 200
GET  /v2/plugin/login/gray-decision?feature=login_v2_oneid&platform=CLI   → 200
GET  /v2/plugin/login/gray-decision?feature=login_v2_ioa&platform=CLI     → 200
POST /console/auth/risk-context?platform=CLI                              → 200
GET  /console/accounts                                                    → 200
GET  /console/validate/refresh-token                                      → 200
```

**三个 gray-decision 是特性开关**（实测返回值）：

| feature | enabled | reason |
|---|---|---|
| `oneid_component` | `true` | `full_rollout` |
| `login_v2_ioa` | `true` | `full_rollout` |
| `login_v2_oneid` | **`false`** | `disabled` |

⇒ 上游对 `platform=CLI` 走 **`oneid_component` + `login_v2_ioa`** 这条路。

### 2.2 `/console/accounts` 返回**真实账号**

```json
{"code":0,"msg":"OK","data":{"accounts":[
  {"uid":"aaaaaaaa-1111-2222-3333-444444444444",
   "nickname":"示例昵称","type":"personal","lastLogin":true,
   "phoneNumber":"13800000009"}]}}
```

⚠️ uid `aaaaaaaa…` 正是本机账号库里已有的第二个账号。
（**注**：上面取值已脱敏，字段名与形状是实测的。）

### 2.3 ⭐ 登录前后的存储长度对比（**证实"实际已登录"**）

用 CDP 读 `localStorage` 的**键名与值长度**（不读值）：

| 键 | 手机登录**前** | 手机登录**后** |
|---|---|---|
| `e418bef1uidsk` | len=414 | **len=1240** ⬆️ |
| `f0b76b70uidsk` | len=234 | **len=700** ⬆️ |

**两个凭据存储项都大幅增长** ⇒ 服务端确实下发了新的、更多的凭据数据。

### 2.4 登录后抓包：**凭据端点未被调用**

登录动作完成后再抓 18 秒，**`/console/login/enterprise` 完全没有出现**。

⇒ 页面没有走"下发凭据"那一步。
**推断**：它在等一个"来认领的客户端"，而我们的监听是挂在
`/console/login/enterprise` 上的 —— 该端点**根本没被触发**。

> ⚠️ **这是当前最需要解释的矛盾**：交接文档记录"凭据来自
> `/console/login/enterprise?state=…` 的响应体"（那是早期探针实测的），
> 但本次真实登录**没有触发该端点**。
> **两种可能**（都未验证）：
> (a) 探针那次触发该端点，是因为它**额外做了某个动作**
>     （比如轮询了取回端点，促发服务端下发）
> (b) 上游行为已变更
> **在验证之前不要改匹配逻辑** —— 改错了会让原本能用的路径失效。

### 2.5 `state` 不一致（值得注意）

| 来源 | state 值 |
|---|---|
| 我们构造的登录页 URL | `80bd2a43-93dc-40cb-a200-44158b52850b` |
| `risk-context` 响应体 `data.state` | `b4182291-cfe6-40f3-8efc-a8bda33220a6` |

**两者不同** ⇒ `risk-context` **新开了一个会话**，不是认领我们 URL 里那个。

⚠️ 对既有实现的影响：`internal/login/cdp.go` 的 `isCredentialEndpoint`
要求 state 等于**我们生成的那个**。若上游实际用 `risk-context` 下发的
新 state 去调端点，**精确匹配会永远匹配不上**。（**推断，未验证**）

### 2.6 `risk-context` 的实测语义

```
POST https://www.codebuddy.cn/console/auth/risk-context?platform=CLI
→ 200 {"code":0,"msg":"OK",
        "data":{"state":"b4182291-…","authUrl":""}}
```

返回 `state` 与 `authUrl`，名称含 `auth` ⇒ 推断承担"开启一次授权会话"职责。

## 六、对「受控浏览器是否真的隔离」的结论

**实测：profile 确实是隔离的。**

```
--user-data-dir=C:\Users\<你的用户名>\AppData\Local\Temp\wbapi-login-3376117659
```

该目录 **本次运行新建**（创建时间 22:55:19，与本次启动一致），
`browser.go` 用 `os.MkdirTemp` 生成，前缀 `wbapi-login-`。

**所以页面里出现的登录态不是"继承了用户自己浏览器的登录态"**，
而是**本次运行期由页面/上游自己建立的**（结合 `risk-context` 新开了 state
这一点，推断是服务端会话 + 该调用带出的账号列表）。

> ⚠️ 这一条推翻了我先前的猜测（"profile 里有上次残留的旧 token"）。
> **记下来**：判断"是否残留"要看文件的**创建时间**，不能只看"文件存在"。

## 七、诊断脚本（可复用，已入库）

| 脚本 | 用途 |
|---|---|
| `inspect-login-page.js` | 读页面可见文本 / localStorage 键名与长度 / 错误元素 |
| `trace-login-network.js` | 监听并打印页面发的请求（URL + 状态码） |
| `dump-login-init-responses.js` | 抓初始化接口的**响应体**（内置脱敏） |

用法（Node 用 DSH 自带运行时）：

```powershell
$node = "<DSH 运行时目录>\node\bin\node.exe"   # 本机为 DSH 自带运行时
& $node docs\panel-dev\inspect-login-page.js <CDP端口>
& $node docs\panel-dev\trace-login-network.js <CDP端口> 22
& $node docs\panel-dev\dump-login-init-responses.js <CDP端口>
```

**脱敏说明**：`dump-login-init-responses.js` 内置 `redact()`，
把 JWT 替换成 `«JWT:长度»`、`*token*` 字段值替换成 `«len=长度»`、
60+ 字符的不透明串替换成 `«opaque:长度»`。**绝不打印凭据原文。**

CDP 端口可从受控浏览器进程命令行取：

```powershell
Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" |
  Where-Object { $_.CommandLine -like "*wbapi-login-*" } |
  ForEach-Object { if ($_.CommandLine -match '--remote-debugging-port=(\d+)') { $matches[1] } } |
  Select-Object -First 1
```
