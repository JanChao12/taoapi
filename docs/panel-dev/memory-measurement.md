# 内存测量方案（Codex 第 28 / 33 轮要求）

> ⚠️ **测量前不得承诺任何具体数字。**
> 本文件先写**方法**，再填**实测值**。未测的项目明确标注"未测"。

---

## 一、口径（委托方已确认）

> **60 MB 指标只约束 `wbapi` 自身常驻内存。浏览器不计入。**

但仍须**分别测量**（Codex 第 28 轮）：

1. `wbapi` 空闲
2. 登录期间**峰值**
3. 结束后**稳定值**
4. **浏览器进程树**峰值

Codex 第 33 轮补充要求：

> 应覆盖**浏览器启动、登录捕获、成功/取消后的清理**，
> 以及 **wbapi 恢复空闲后的占用**；
> **分别记录 Go 进程和浏览器**，
> **不能只测启动后的 Go RSS**。

---

## 二、为什么要单独写方法（而不是直接报数字）

本项目**踩过一次内存测量事故**（见全局 AGENTS.md）：

> 看到进程 RSS=67MB 而 Go 堆只有 1.27MB，我推断"是 Go 运行时在 Windows
> 不归还内存"，于是加了 `GOMEMLIMIT` + `SetGCPercent(50)`。
> 实测 RSS **零变化**，却让 GC 频率翻倍。
> 真相是：**我自己的测量方法有问题**（强杀进程导致 TLS 缓冲未释放、
> 日志重定向的管道缓冲计入进程）。

⇒ 所以本次测量**先确定方法**，且每个数字都要说明**是怎么测的**。

## 三、测量方法

### 3.1 测什么进程

| 对象 | 怎么定位 |
|---|---|
| `wbapi` 自身 | 按**进程名** `wbapi.exe` |
| 受控浏览器进程树 | 按**命令行含 `wbapi-login-`** 过滤（只统计我们创建的，不含用户自己的浏览器） |

⚠️ **必须按命令行过滤浏览器** —— 否则会把用户自己的 Chrome 算进去，
数字完全失真。

### 3.2 测什么指标

用 `WorkingSet64`（工作集，即 RSS）。

⚠️ **不用 `PrivateMemorySize64`**：那是提交大小，与"常驻内存"不是一个口径，
且 Windows 上差异很大（会把保留但未触碰的算进来）。

### 3.3 什么时候测

| 时点 | 说明 |
|---|---|
| T0 基线 | `wbapi` 启动后、未做任何操作 |
| T1 登录中 | 浏览器已启动、等待用户登录 |
| T2 捕获时 | 已捕获到凭据、正在解析落盘 |
| T3 结束稳定 | 登录流程结束、浏览器已退出、GC 后 |
| T4 恢复空闲 | 再等一段时间，确认回落 |
| B峰值 | 浏览器进程树的工作集之和（各时点取最大） |

⚠️ **每个时点至少采样 3 次取中位数**，避免瞬时抖动。

---

## 四、实测结果（2026-10-06 实测）

> 口径：`WorkingSet64`（即 RSS），每点采样 3 次取中位数。
> 环境：本机 8 GB 内存，3 个真实账号，Windows。

### 4.1 主表

| 时点 | wbapi 自身 | 受控浏览器进程树 |
|---|---|---|
| **T0 空闲基线**（全新实例） | **16.18 MB** | 未运行 |
| **T1 浏览器已启动**（等待登录） | **15.78 MB** | **921.64 MB**（12 进程） |
| **T2 登录完成/捕获** | （见 4.2 说明） | — |
| **T3 结束后稳定** | **15.75 MB** | 未运行 |
| **T4 恢复空闲**（+15 秒） | **15.75 MB** | 未运行 |
| T6 取消并清理后 | 15.75 MB | 未运行 |

### 4.2 重复登录不增长（Codex 第 28 轮要求）

连续 **5 轮**"启动登录 → 中途取消 → 清理"，每轮采样：

| 轮次 | wbapi | 浏览器进程数 |
|---|---|---|
| 1 | 15.75 MB | 14 |
| 2 | 15.86 MB | 14 |
| 3 | 15.86 MB | 14 |
| 4 | 15.86 MB | 14 |
| 5 | 15.82 MB | 13 |
| 结束后 | **15.82 MB** | 0 |

⇒ 波动约 **0.1 MB**（噪声量级），**未观察到持续增长**。

### 4.3 ⭐ 核心结论（**Codex 第 34 轮给定措辞，照此表述**）

> **已测时点的 wbapi Working Set 中位数为 15.75–16.18 MB，低于 60 MB 红线；
> 5 轮取消与清理未观察到持续增长。捕获瞬间峰值及长时间运行尚未测得。**

⚠️ **不得夸大的三点**（Codex 纠正）：

1. **不能说"全程都在这个范围"** —— 每点 3 次采样取中位数会**过滤短暂峰值**。
2. **不能说"捕获没有抬升"** —— T1→T3 之间**没有连续采样**，
   不能声称期间无跳变。
3. **不能把结论归纳成"网页登录总体内存影响可以忽略"** ——
   浏览器进程树占约 **920 MB**（虽可能高估），
   **在 8 GB 机器上是明显的临时资源开销**，影响使用体验。
   它不违反"只约束 wbapi"的红线，但**必须与 wbapi 的数字并列说明**。

### 4.3.1 应当并列表述的两件事

| 对象 | 数字 | 说明 |
|---|---|---|
| **wbapi 自身** | 15.75 ~ 16.18 MB | 低于 60 MB 红线 ✅ |
| **浏览器进程树** | 约 **920 MB**（12 进程求和，可能高估） | 登录期间的**临时**开销，登录结束即释放 |

⇒ 发布说明**必须两者都写**，否则读者会以为"总共只要 16 MB"。

### 4.3.2 本轮有效的验收证据（Codex 点名认可）

- 成功、取消后**浏览器与临时 profile 均被清理**
- **连续取消未见增长**（5 轮）
- 登录互斥属于**设计边界**，不是"漏测并发登录"

### 4.4 未测项（**不得用推断值填充**）

- **T2（捕获瞬间峰值）**：未测得。真实"读取并解析"只占毫秒级，
  采样点无法可靠命中。
  - 补充办法（Codex 建议）：记录**新进程的 `PeakWorkingSet64`** ——
    它能给出进程生命周期的驻留峰值，但**不能准确归因到捕获那一刻**。
- 长时间连续运行的占用（留作后续验证，**不阻塞本次验收**）

### 4.5 🔴 **未解释的观察**：曾见到一个实例报 70.27 MB

⚠️ **这是一个尚未解释的观察，写下来而不是"解释掉"。**

**观察到**：UI 验收期间启动的一个实例（PID 17364，新 exe，8787 端口）
**稳定报 70.27 MB**（`PeakWorkingSet64` 70.3 MB），**高于 60 MB 红线**。
而同期其它实例为 16~27 MB。

**已做的证伪实验（都**没有**支持我最初的解释）**：

| 我的假设 | 实验 | 结果 |
|---|---|---|
| "服务过 HTTP 请求所以变大" | 干净实例访问面板+app.js 40 轮 | ❌ 仅 20.08 → 21.44 MB |
| "跑过 UI 验收（点过网页登录）所以变大" | 在干净实例上重跑 UI 验收（14/14 通过） | ❌ 仅 25.64 → 27.6 MB |
| "登录流程启动过浏览器所以变大" | 该实例 `login/status` 为 `idle`，且无浏览器残留 | ❌ 未能归因 |

**同时观察到**：同为"新 exe 刚启动"，不同时刻测得 **24.07 / 20.08 MB**，
而更早（旧 exe）测得 **16.18 MB** —— 说明**同一二进制在不同环境状态下
读数就有数 MB 波动**。

**当前的诚实结论**：
- **不能断言这是代码缺陷**（三条证伪都不支持）
- **也不能断言它无害**（没有解释清楚）
- 可能与**机器内存压力**有关（当时可用内存仅 1.86~2 GB / 7.83 GB），
  但这**只是推测，未验证**

⚠️ 这与本项目**既往教训同类**（全局 AGENTS.md 记录过：RSS 67 MB
而 Go 堆仅 1.27 MB，真相是测量/环境问题而非代码问题）——
所以**先证伪、再改代码**，不要基于未验证的解释行动。

**待办**：在**内存压力小**的环境下重复测量，确认 70 MB 能否复现。
**在此之前不要把它写进发布说明，也不要据此改代码。**

## 五、🔴 测量陷阱（本项目实际踩过的，**测量前必读**）

### 5.1 低 Working Set 会让数字失去意义（**本次新发现**）

**实测**：一个闲置 9 小时的 `wbapi` 报 **0.05 MB**，而刚启动的报 **16.18 MB**。

⚠️ **措辞纪律（Codex 第 34 轮纠正）**：
"被换出到磁盘"**不是这些数字单独能证明的** —— 工作集裁剪
不一定意味着页面写入磁盘。只能说"观察到 Working Set 异常低"。

⚠️ **`< 1 MB` 只能作为脚本的复核提示，不能当作普遍的"数据不可信"判据。**
应优先核对：**进程存活 / 监听端口 / 启动时间 / 服务响应**，
并注明该值**不适合作为活跃负载基线**。

⇒ 实践做法：**始终测量刚启动的实例**，不要测闲置很久的进程。

### 5.2 僵尸进程（已退出但句柄未回收）

本次还遇到：`Get-Process` 仍能找到某 PID，但
`HasExited=True`、端口**未监听**、`taskkill` 报 "no running instance"。

⇒ 这类"进程"的内存数字毫无意义。测量前应确认**端口在监听**。

### 5.3 采样取中位数会过滤峰值

⚠️ 中位数抗瞬时抖动，但**代价是看不到短暂峰值**。
若要抓峰值，应改用 `PeakWorkingSet64` 或高频连续采样 —— 并在报告里
说明用的是哪种口径。

### 5.4 强杀进程会让数字失真

`Stop-Process -Force` 跳过清理，TLS/日志缓冲可能未释放 ⇒ 数字偏高。
应优先**优雅退出**。

### 5.5 日志重定向的管道缓冲会计入进程

若 stdout 被重定向到管道，缓冲也算它的内存。测量时应避免。

### 5.6 共享内存重复计数

多个浏览器子进程共享部分内存（如渲染器共享的只读段），
**简单相加会高估**。所以 921 MB 是**上限估计**，应如此表述。

### 5.7 测错对象

必须按**命令行含 `wbapi-login-`** 过滤浏览器进程 ——
否则会把用户自己的 Chrome 算进来（本次实测中用户浏览器有 9 个进程常驻）。

### 5.8 PowerShell 只读自动变量

脚本里**不能**用 `$Pid` 作参数名 —— 它是 PowerShell 的只读自动变量，
会报 `Cannot overwrite variable Pid because it is read-only`（已踩）。
本脚本用 `$TargetPid`。

## 六、复现方式

```powershell
# 1. 启动一个全新实例（不要用闲置很久的）
cd "D:\download\DSH\构建反代项目\workbuddy-api"
.\wbapi.exe serve --addr 127.0.0.1:8901

# 2. 采样（把 <PID> 换成上面那个进程）
powershell -ExecutionPolicy Bypass -File ".\内存采样.ps1" -Label "T0-空闲" -TargetPid <PID>

# 3. 触发登录（另开一个窗口），期间再采样
go run ./tools/refreshprobe -step capture
```
