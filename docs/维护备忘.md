**计数（以原始结果表为准）**：
- models：**8/11 HTTP 成功**（原值 + 去空白 + 6 种扰动），被拒 3 个
- billing / chat：**2/11 成功**（两种原值形式），**9/11 被拒**
- v3config：**11/11 HTTP 200**

**结论（三条，全部实测；含 Codex 第 8 轮的收窄）**：

1. **`/v2/.../models` 与 billing/chat 的鉴权口径不同** ——
   同一组扰动凭据在 models 得到成功响应，在 billing/chat **被拒**。
   ⇒ **「models 请求成功」不足以证明 billing/chat 鉴权成功。**
   ⚠️ 这不证明上游采用哪种签名校验机制，也不推广到所有账号/凭据。

2. **`/v3/config`：HTTP/业务成功既不保证、也不代表什么** ——
   准确表述（Codex 收窄）：
   > v3config 的 HTTP／业务成功**不保证**返回非空目录；
   > 返回非空目录**也不保证**凭据能用于 billing/chat。
   - 无凭据/垃圾值 ⇒ 200 但 **`data.models` 为空（252 字节）**
   - 尾 4 位扰动 ⇒ 200 且 **22 条**（与真 token 相同），**但 billing/chat 拒绝它**
   ⇒ **HTTP 200 绝不能作为"该端点可用"或"凭据有效"的判据。**
   ⚠️ **不要把它命名为"格式宽松"或"按凭据门控"** —— 本实验**没有定位**
      它到底检查什么（只知 Authorization 的有无/取值**影响**内容，
      不能排除其他头联合参与）。

3. **`exp` 未过期** ⇒ 以上**都**不是"自然过期"情形。
   **自然过期 / 官方撤销 token 的行为仍未实测**；本地解析到未过期 `exp`
   **不等于**完成了签名验证。

**未排除的替代解释**：缓存头全为空、未观察到缓存行为；未测其他认证头的影响。

**对本项目实现的含义**（`fetchV3Models` 现状）：
- 已同时检查 `code == 0` 且 `data.models` **非空**，空则按失败处理 ⇒ 能挡住
  "坏凭据拿 200 但空目录"这一情况。**这个防护是目录加载校验，不是健康验证。**
- ⚠️ **非空目录不能用于清除账号异常标记**（billing/chat 才相关）。
- ⚠️ 静态兜底应保留"本次拉取**失败**"的事实，不能显示成"上游实时目录获取成功"。
- ⚠️ **空目录可能是合法的"无模型权限"状态** ⇒ 可作为加载失败处理，
  但**不要**自动归类为凭据失效。


**上游疑似变更时**：先跑 `go test ./...`，红掉的 fixture 测试就是嫌疑契约；然后按 `upstream-contract.md` §十一 的复现方式直连重测，更新 fixture 与文档日期。**不要信中间层**（wild-work 曾致 reasoning 偏差 18 倍、模型 31→17）。

**未实测项（改代码前先补测）**：签到"首次成功"的真实响应体（当前只有"已签到"样本）；`kimi-k2.8-preview`（委托人明确不测）；国际版站点；`space-bunny`/`glm-5.3` 之外的档位行为。

## 二、架构红线（有测试背书，不许绕）

1. **provider 层不许 import app**：换号逻辑通过 `accountChatter` 接口反向抽象（`failover.go`），加新 provider 时照此模式，别让 app 依赖具体渠道包。
2. **chat 请求绝不能带 `X-Refresh-Token`**：refresh token 只出现在 refresh 端点，且不进日志/事件/Git。断言在 `testutil/fake_upstream.go`。
3. **只监听 `127.0.0.1`**。自用工具，不改成对外网卡。
4. **加密失败绝不退回明文**（`storage/file.go`）：DPAPI 失败就是不写文件，`auth_test.go` 断言"失败时不留文件"与"密文里搜不到明文 token"。非 Windows 是显式报错的占位实现，不是明文降级。
5. **403 不自动判封号**：`banned` 必须有上游业务证据；未知 403 走 `transient`/`unknown` 短期隔离。防一次网络抖动废号。
6. **换号上限 2 个账号**、参数类错误（如档位不支持）不换号——白耗配额。见 `failover_test.go`。

## 二之二、🔴 DSH 接入的两个必踩坑（2026-10-05 委托人真实接入时暴露）

DSH 是本项目的**首要客户端**。接入时先看这一节，能省两轮排查。

### 坑 1：`No API key for provider: xxx`（请求根本没发出去）

**现象**：DSH 报红 `处理失败 / 本轮运行失败  No API key for provider: me`，
错误码 `PI_AI_ERROR`。

**要点**：`PI_AI_ERROR` 是 DSH 的 `llm-pi-ai` 层报的，说明**请求没到我们的 8787**，
不是反代的错。DSH 在本地就因缺密钥拦下了。

**DSH 的密钥规则**（源码 `dsh-client-ui-settings-models` 实测）：

```js
function deriveKeyRef(provider) {
  return `${provider.toUpperCase().replace(/[^A-Z0-9]+/g, "_")}_API_KEY`;
}
```

即按 **provider 名自动推导**环境变量名：`workbuddy` → `WORKBUDDY_API_KEY`、
`me` → `ME_API_KEY`。**在 DSH 设置界面的「API 密钥」框填任意非空值并保存**，
DSH 会自动按此规则存进凭据、并在配置里记录 `apiKeyEnv`，不需要手配。

**本反代不校验 key**（实测：不带 `Authorization` 也是 200），所以填什么值都行。

**⚠️ 文档历史缺陷**：`docs/dsh-workbuddy.yaml` 早期写的是
`apiKeyEnv: WBAPI_LOCAL_KEY` —— 这个变量**本机并不存在**，
照抄必然触发本坑。已改为 `WORKBUDDY_API_KEY` 并写明推导规则。

### 坑 2：两个 400（进了反代但解析失败）

**现象**（注意这次**是我们**返回的，说明密钥已通）：

```
400 {"message":"请求体不是合法 JSON: json: cannot unmarshal array into Go struct
     field ChatCompletionRequest.tools.0 of type uint8", ...}
400 {"message":"... ChatCompletionRequest.messages.6.content of type string", ...}
```

**真因两条**：

1. `types.go` 曾写成 `type json_RawMessage = []byte` —— `[]byte` 不实现
   `json.Unmarshaler`，JSON 数组会被当字节数组解，于是报 `uint8`。
   必须是 `json.RawMessage`。（注释当时已写"是 json.RawMessage 的别名"，
   与代码不符，属笔误。）
2. `messages[].content` 只接受 `string`，但 OpenAI 兼容客户端会发**多模态数组**
   （`[{"type":"text","text":"hi"}]`）。已加 `InboundMessage` + `StringOrParts`
   兼容「字符串 / 分片数组 / null / 缺失」四种形状。

**顺带修掉的有损转发**：`app/chat.go` 原先用 `json.Marshal(req)` 回写请求体，
结构体是有损中间表示，`content` 数组与 `tools` 的未知字段会在往返中丢失/变形。
已改为 `rewriteModel()`：**只替换顶层 `model` 一个字段，其余逐字节透传**。
改这块时务必保持这个原则 —— 上游请求体不做结构体往返。

**护栏**：`protocol/openai/types_test.go`（tools 数组、content 四种形状）+
`app` 的 `TestChatAcceptsDSHShapedRequest`（端到端断言转发保真）。
两条都做过**反向对照**：还原旧代码会复现线上同款报错。

**教训**：我们的入站解析**不能比 OpenAI 实际协议更窄**。客户端发什么形状，
先接受再判断，别用我们自己的窄结构体去拒绝合法请求。

## 三、关键设计"为什么"

- **流式"先探测再写响应头"**：一旦写出 200 + 首 SSE 帧，客户端已收到 200，换号在协议上不可能。所以 `TryChat` 先拿到上游第一个事件、确认账号可用，才让调用方写头（`failover.go` 包注释）。改任何 chat 链路时保持这个顺序，`TestFailoverAfterStreamStartedIsImpossible` 会守住它。
- **pool 只看"最早到期包"**：委托人明确否决"7 天临期总量"排序（原话见 `pool.go` 包注释）。`pool_test.go` 用 A(10-05/1分) vs B(10-06/5000分) 断言必须选 A——**别"优化"回去**。
- **`Status("")` 归一为 `normal`**（`pool.Normalize`）：磁盘加载缺 status 字段时零值是 `""`，若不归一，所有账号会被静默排除（服务能启动但一个号都不用，曾真实发生）。
- **DPAPI 用 syscall 不用 cgo**：保住"纯 Go 单 exe、离线可构建"；加熵绑定本机。改存储格式时保持 `Codec` 接口语义（失败返回错误，不降级）。
- **非流式 = 自己聚合同一条上游流**：因为上游强制 stream，不存在"发 stream:false 等 JSON"的路径。
- **`Router.Models()` 必须排序**：底层 map 迭代随机，不排序会导致每次刷新模型列表顺序都变（委托人反馈"顺序乱跳"）。有 `TestModelsOrderIsStable` 守着。
- **`in_use` 与真实调度同源**：`/api/accounts` 的 `in_use` 用 `pool.Selector` + 同一份快照算出，不是另写一套判断——否则面板显示的号和实际转发的号会不一致。`TestAccountsInUseMatchesSelector` 守着。
- **403 不自动判封号**：`classifyFailure` 把 401/403 记为 `auth_expired`（可尝试 refresh），只有上游明确的封禁业务证据才 `banned`。`TestClassifyNeverReturnsBanned` 守着——当前实现**不应有任何路径**产生 banned。

## 三之二、Codex 评审留下的护栏（改这些地方前先看测试）

本项目与 Codex 做了 8 轮对抗式评审，几条关键否决已落成测试：

| 评审结论 | 守它的测试 | 改错了会怎样 |
|---|---|---|
| 流式不能提前写头（否则换号失效） | `TestFailoverAfterStreamStartedIsImpossible` | 流式换号静默失效 |
| 换号最多 2 个账号，参数错误不换号 | `TestFailoverNeverTriesMoreThanTwoAccounts`、`TestNoFailoverOnUnsupportedReasoning` | 白耗备用号配额 |
| 403 ≠ 封号 | `TestClassifyNeverReturnsBanned` | 一次网络抖动废掉账号 |
| 额度未知 ≠ 额度为零 | `TestPickRequiresKnownCredits` | 新导入账号永远不可调度 |
| 加密失败绝不退回明文 | `TestSaveNeverFallsBackToPlaintext` | 凭据明文落盘 |
| 空 ExpireAt 不参与临期判定 | `TestPickIgnoresPackagesWithoutExpiry` | 用零值冒充"永不过期" |
| 已过期但上游仍返回的包仍算数 | `TestPickUsesEarliestPackageNotSum` 相关断言 | 误判可用额度 |

  go test ./...                          # 默认：不碰注册表，20+ 纯逻辑用例照跑

  但 Go 仍会**编译**出 `autostart.test.exe`（要跑才知道跳不跳）。
  所以现状是"**文件还在，但行为无害**"。
  若将来发现告警仍然出现，说明卡巴是按**文件/路径**而非**行为**报的，
  那种情况下这个门控无效，需要改用杀软排除路径 —— 不要误以为改坏了。

  **⚠️ 代价（有意取舍）**：默认不跑 = 注册表读写链路平时不被覆盖。
  本包已拆成两层：命令行拼接/路径校验等**纯逻辑**永远跑（覆盖"开机静默
  不启动"这类最难查的错），**真实注册表读写**只在显式开启时跑。
  **改动 `autostart_windows.go` 的注册表代码后，必须显式跑一次上面那条命令。**

  为了让"跳过"不是无声的，包退出前会打印一行汇总（TestMain 实现）：

  - `[autostart] ✅ 本次已真实读写注册表：注册表链路被覆盖`
  - `[autostart] ⚠️ 本次未真实读写注册表：...要完整验证请设置 WBAPI_RUN_REGISTRY_TESTS=1`

  > 这行汇总最初写成一条普通测试，结果在 `-run` 过滤下**报了假阴性**
  > （`TestEnableDisableRoundTrip` 明明跑了，汇总却说未覆盖 ——
  > 因为按名称排序它排在汇总之前）。**会撒谎的检查器比没有检查器更糟**，
  > 所以改成 TestMain 在全部测试结束后统一汇报。

  旧变量 `WBAPI_SKIP_REGISTRY_TESTS=1` 仍被识别，只打印一句"已不再需要"
  的提示，**不报错**（避免老文档/老习惯造成困惑）。
- **Go 不在 PATH**：构建前先定位 Go 安装路径再调 `go`，或用绝对路径。
- **PowerShell 写文件默认带 BOM**：`Out-File`/重定向产生的 UTF-8 带 BOM，Go 的 JSON 解析会报 `invalid character '\ufeff'`。写 fixture/配置用 `New-Object System.Text.UTF8Encoding($false)` + `[System.IO.File]::WriteAllText(...)`。
- **`.ps1` 脚本反过来：必须带 UTF-8 BOM**（2026-10-05 实测踩到）。本机 shell 是
  **Windows PowerShell 5.1**（不是 pwsh 7），它读**无 BOM** 的 `.ps1` 时按 ANSI(GBK) 解码，
  中文注释变乱码并破坏字符串终结符 → `Unexpected token '}'` / `missing the terminator`。
  写 `.ps1` 用 `New-Object System.Text.UTF8Encoding($true)`。
  **规律**：`.go`/`.json`/`.yaml` → **无** BOM；`.ps1` → **有** BOM。
- **本机默认禁止运行 .ps1**（ExecutionPolicy）。测试脚本用
  `powershell -NoProfile -ExecutionPolicy Bypass -File <脚本>`，不要直接 `& .\x.ps1`。
- **`Join-Path` 遇到绝对路径会拼错**（实测踩到）：`Join-Path $root "C:\tmp\x.exe"`
  产出 `$root\C:\tmp\x.exe`。处理用户传入的输出路径要先
  `[System.IO.Path]::IsPathRooted()` 判断，再 `GetFullPath()` 归一。
- **复现脚本不能用 .NET `HttpWebRequest`**：它禁止用 `Headers.Set` 设 `User-Agent`/`Referer`，用 `HttpClient`。
- **git 是后期才 init 的**：首个 commit 是"基线"。改动前确认工作区干净，别把未提交的实验混进基线之后的小步提交。

### 🔴 绝不用 PowerShell 读写 `accounts.json`（2026-10-05 真实事故）

**发生过什么**：用 `Get-Content -Raw | ConvertFrom-Json` 读账号文件时，
`ConvertFrom-Json` 因文件里的中文（包名）编码问题**解析失败返回 null**，
紧接着的 `[System.IO.File]::WriteAllText($f, ($j | ConvertTo-Json))`
把 `accounts.json` **写成了 0 字节** —— 三个真实账号的凭据全丢。

**为什么危险**：账号文件里是唯一的凭据副本（token 加密存储），
被清空后只能靠重新导入恢复；如果源（如 CodeBuddy 客户端）已登出，就真丢了。

**正确做法**：
- 读账号状态走 `wbapi.exe status` / `auth list` / 面板 API（Go 的 JSON 解析 + 显式字段映射）
- 改账号走 `wbapi.exe auth import/remove` 或面板
- 确实要用 PowerShell 做**只读检查**时，用
  `[System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes($f))` 取文本后只做字符串匹配，
  **绝不 ConvertFrom-Json 之后再回写**
- 任何对 `accounts.json` 的写操作前先 `Copy-Item` 备份

**恢复手段**：`wbapi auth import --from-wild-work <目录>` 重新导入，
额度会自动刷新（见 §四）。

### 🟡 内存测量：必须用"干净启动"的进程（2026-10-05 踩坑记录）

**实测基线（可信数据）**：

| 状态 | RSS |
|---|---|
| serve 无账号 | 9.2 MB |
| serve 有 3 个账号 | 16.2 MB |
| 跑 6 次真实对话后 | 17.7 MB |
| 静置 60 秒 | 17.6 MB（不增长）|
| Go 堆（heapAlloc） | 1.8 MB |

**曾测出 66-67 MB 的假数据，原因是测量方法错了**：

1. 用 `Stop-Process -Force` **强杀**上一个 wbapi，立刻起新进程再测 ——
   被强杀的进程 TLS 连接未正常关闭，内核 socket 缓冲未释放，
   累积资源被计入新进程；
2. 启动时加了 `-RedirectStandardError <file>`，**管道缓冲也计入进程**。

**正确测法**：
- 先 `Stop-Process` 停掉所有 wbapi，**等 2-3 秒**让内核回收，再启动新进程
- 不要挂 `-RedirectStandardError`（要看日志就用 `serve -v` 前台跑，或写文件后立刻断开）
- 等 15 秒后测量（启动期有 TLS 握手 + 模型目录拉取）
- 用 `/status` 的 `memory.heapAllocBytes` 交叉验证：
  **Go 堆只有 1-2 MB，它才是代码的真实占用**

**⚠️ 上面"等 2-3 秒"偏短，实测应为 20 秒（2026-10-05 修正）**：

同一次会话里我先按"等 3 秒"测到 **67 MB**，改用「停→等 20 秒→**确认进程数为 0**→
启动单一实例」后测得 **16.02 MB**（Go 堆 1.5 MB）。
即强杀后内核回收**可能要十几秒**，2-3 秒不够。

**可靠的测量流程（照抄即可）**：

```powershell
# 1) 停掉所有相关进程（注意可能有不只 wbapi 一个名字）
Get-Process | Where-Object { $_.ProcessName -like '*wbapi*' } | Stop-Process -Force
# 2) 等 20 秒，并【确认真的归零】—— 没归零就不要开始测
Start-Sleep -Seconds 20
Get-Process | Where-Object { $_.ProcessName -like '*wbapi*' }   # 必须无输出
# 3) 启动【单一】实例，等 15 秒（TLS 握手 + 模型目录）
# 4) 读数前再确认只有 1 个进程、且端口是自己的
```

**判定"这个数字是假的"的快速特征**：RSS 远大于 Go 堆且**比值 > 10 倍**
（本次 67 MB vs 1.5 MB），或多次重启读数**一模一样**（真实值会随负载小幅浮动）。

**不要盲目加 `GOMEMLIMIT`/`SetGCPercent`**：曾基于 66 MB 的假数据加过，
实测对 RSS **零效果**（67.29 → 67.29 MB），却让 GC 频率翻倍 —— 已回滚。

#### ⚠️ 第三次踩同一个坑：67 MB 的另一个成因（2026-10-05，同一会话内）

**现象**：强杀旧进程 → 等 3 秒 → 启新进程，RSS 又是 **67 MB**（而干净测量是 17.5 MB）。

**这次的真因不是管道缓冲，是"残留进程占用端口"**：
排查时我用 `git worktree` 编了个旧版做 A/B 对比，进程名是 **`wbapi_old`**。
后续 `Get-Process wbapi` **抓不到它**（名字不同！），
于是它在后台一直占着 8793 端口、持有约 66 MB；
新进程因端口被占**启动即退出**，我读到的 RSS 其实是**别的进程/残留资源**。

**能一眼识破的关键证据**（本次就是靠它定性的）：
- `Get-NetTCPConnection -LocalPort <port> -State Listen` 显示端口**仍被占用**，
  且 `OwningProcess` 指向一个**你不认识的 pid**；
- A/B 两组读数**完全一样**（都 66.67 / 66.85 MB）→ 若真与代码有关，不可能一样；
- 交叉指标严重背离：Go 堆仅 1.1 MB vs RSS 67 MB（**差 50 倍以上就当它是脏数据**）。

**新增到"正确测法"的第 5 条**：
5. 启动后**先确认进程真的活着、端口是自己的**再读数：
   ```powershell
   Get-Process wbapi,wbapi_old -ErrorAction SilentlyContinue |
     Select-Object Id,ProcessName,@{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,2)}}
   Get-NetTCPConnection -LocalPort 8787 -State Listen
   ```
   做过 A/B 测试后，**必须按进程名逐个清理**（`wbapi_old` 这种临时名最容易漏）。

**共性**：三次 67 MB 假数据，成因各不相同（强杀未回收 / 管道缓冲 / 残留占端口），
**但结构完全一样 —— 我的测量方法有问题，不是代码有问题**。
看到 RSS 异常大时，**默认假设应该是"我测错了"**，先做对照实验再谈代码。

## 六之二、🔴 面板"改了但看不到" → 先查缓存，别先怀疑代码（2026-10-05 真实误判）

**委托人反馈**：面板上「⚡ 反代使用中」徽章没有、模型列表没有「刷新」按钮，
并直接问"是不是你之前回滚掉了或者是忘了做"。

**实际情况**：代码**一直都在**（`app.js` 的 `a.in_use` 渲染、`index.html` 的
`btn-refresh-models`、`style.css` 的 `.badge-inuse`），服务端下发的也是新文件。
**真正原因是浏览器强缓存了旧副本** —— `panelHandler` 用 `http.FileServer` 服务
`embed.FS`，**没有设置任何 `Cache-Control`**；而 `app.js` / `style.css` 文件名固定，
浏览器于是按启发式规则长期使用本地旧副本。服务端换了代码，浏览器永远拿旧的。

**已修**：`panelHandler` 统一加 `Cache-Control: no-cache, must-revalidate`
（配合 FileServer 自动产生的 `Last-Modified`/`ETag`，未变动时 304，开销极小）。

**排查顺序（重要，避免再次误判）**：

1. 先确认服务端下发的是不是新内容 —— 直接取包比对，**不要看浏览器**：
   ```powershell
   (Invoke-WebRequest http://127.0.0.1:8787/panel/app.js -UseBasicParsing).Content -match '反代使用中'
   (Invoke-WebRequest http://127.0.0.1:8787/panel/app.js -UseBasicParsing).Headers['Cache-Control']
   ```
2. 服务端是新内容 → **就是客户端缓存**，让用户 Ctrl+F5 / 无痕窗口，不是代码问题。
3. 服务端也是旧内容 → 才去查 exe 是否重新构建过（`serve` 用的是编进二进制里的
   `embed.FS`，**改完 CSS/JS 必须重新 `go build` 并重启**，光改源文件无效）。

**教训**：用户说"功能没了"时，**不要先回答"我没做"或"没回滚"**——
先取得服务端实测证据；本次凭 `git log` + 下发内容两条证据才敢下结论。

## 六之二之二、🔴 模型列表的两层"刷新"语义（2026-10-07，委托方问出）

> **"刷新按钮现在能刷新最新的动态列表了吗"—— 答案曾经是"不能"，现已修复。**
> 这条必须记住，因为"刷新"这个词在面板里有**两层完全不同**的含义。

### 两层刷新

| 层 | 动作 | 数据来源 | 修复前 | 修复后 |
|---|---|---|---|---|
| **① 视图层** | 重新读 Router **内存** | `/api/models` → `ModelsWithoutAliases()` | ✅ 一直是这个 | 同左 |
| **② 服务端** | 让服务**真的去上游重拉** | `POST /api/models/refresh` → `Router.Refresh` | ❌ **不存在** | ✅ 新增 |

**修复前**：按钮只做① ⇒ 上游改了模型（新增/下架/改价），点刷新**看不到**，
必须**重启服务**（内存只在启动时由 `registerOnePlatform` 写一次）。

**实测判别法**（以后想验证"是否真的上网"直接用）：
`/api/models` 读内存只要 **20–85ms**；真去上游拉要 **1–2 秒**（2339ms 实测）。

### 🔴 `Router.Refresh` 与 `Register` 必须分开（别合并）

- `Register` 是**合并**语义（只写不删）⇒ 上游**下架**的模型会**永远滞留**，
  用户选到只会报错。**只适合启动时用一次。**
- `Refresh` **先删该 provider 旧条目再写**（原子，同一次持锁），
  且**失败/返回 0 条都不清空原列表** —— 否则一次上游抖动就把好列表清成空。
- 证伪实验：注释掉 Refresh 里的删除步骤 ⇒
  `TestRefreshRemovesDelistedModels` 立刻红。

### 接口契约

- `POST /api/models/refresh`（**套 `guardManagementAPI`**：有副作用 ⇒ 必须防 CSRF；
  实测：无令牌 403、GET 405）
- 响应：`{ok, total, failed, sources:[{prefix, ok, count, error}]}`
- **失败不清空**：某平台挂了 ⇒ 保留该平台原有列表，前端**如实说明**
  "哪个平台没更新，其原有列表仍在使用"（红色 `.hint-text.bad`）
- **逐平台重试**：复用 `attemptModels`（与启动注册同一套"逐个账号重试"）

### 本机无 gcc ⇒ 并发原子性怎么验证

`TestRefreshIsAtomicUnderConcurrentRead`：并发刷新时反复读路由，
断言"数量只能是旧值或新值，**绝不为 0**"（删除与写入同一次持锁内完成）。
**不声称"并发已验证"** —— 这只覆盖"看不到空中间态"这一面。

## 六之三、🔴 跨 origin 探活的三个坑（2026-10-05，Codex 第 19 轮评审 + 我实测复现）

> **背景**：`settings.js` 的 `pollRestart` 负责"改端口重启后自动重连"。
> 它用 `fetch(newOrigin + '/healthz', {mode:'no-cors'})` 判断新地址是否就绪。
> Codex 第 19 轮指出这里有问题，**我做了 4 组真实 Chrome 实验，全部复现**。
> 这 4 条里**有 3 条是我自己的方案错**（详见 `codex-consult/19c`~`19f`）。

### 坑 1：`mode:'no-cors'` 无法判断服务是否就绪 —— **503 也会被当成"通了"**

实测（真实 Chrome，对恒定返回 503/404/200 的三个服务各跑一次）：

| 服务端实际 | fetch 结果 | `type` | `status` | `ok` |
|---|---|---|---|---|
| **503** | **resolved** | `opaque` | **0** | false |
| **404** | **resolved** | `opaque` | **0** | false |
| 200 | resolved | `opaque` | **0** | false |

**三者完全无法区分。** opaque 响应把 `status` 固定 0、`ok` 固定 false，
唯一可观察的就是"resolve 了" —— 而 503 也 resolve。

**后果**：探针退化成"端口是否有人监听"。子进程已 bind 但 handler 未就绪、
甚至**新端口上跑的是完全无关的另一个程序**，都会被判为 ready 并跳转 →
用户落在白屏/404，**比"提示手动刷新"更糟**（后者至少告诉用户去哪）。

**修法**：改用**普通 CORS fetch**，并按下面 §四条件判据导航。

### 坑 2：只查 `response.ok` 仍不够 —— **通配 CORS 的无关服务会被误判**

实测：无关服务返回 `Access-Control-Allow-Origin: *` + 200 时，
浏览器得到 `resolved:true, status:200, ok:true`，**且能读到 body**。

**后果**：一个恰好开了通配 CORS 的本机服务会被当成"我们的服务已就绪"。
**这恰恰是 Codex 第 12 轮否决"`/api` 开通配 CORS"时担心的那类东西** ——
差点用一个更隐蔽的方式放回来。

**修法**：不能只查 `ok`，必须校验**服务标识 + ready + restartId**（见 §四条件）。

### 坑 3：新服务只允许**自己的** origin → 自动重连 **100% 失效**

实测：页面在旧 origin（`127.0.0.1:8899`）探测新端口（8811），
若新服务白名单只写自己的 `8811`：

```
8811 只允许自己 origin   → resolved:false, TypeError: Failed to fetch   ← 功能全废
8812 允许旧 origin       → resolved:true,  ok:true, body 可读
8813 允许旧+新           → resolved:true,  ok:true, body 可读
8814 允许任意回环        → resolved:true,  ok:true, body 可读
```

**极易踩**：直觉上"我的服务只认自己的地址"听起来最安全，**实际直接把功能杀死**。
且**测试若写成"页面在新 origin 上探测新端口"会全绿，而生产是坏的**。

**修法**：白名单必须包含**本次重启的旧 origin**（见 §四）。

### 坑 4：旧 origin 不能按**监听地址**推导 —— `localhost` ≠ `127.0.0.1`

实测：页面用 `http://localhost:8830` 打开时，`location.origin` 是
`http://localhost:8830`；此时白名单写 `http://127.0.0.1:8830` 会**被拒**（`Failed to fetch`），
写 `http://localhost:8830` 才放行。

**后果**：若按监听地址推导旧 origin，**所有用 `localhost` 打开面板的用户自动重连全失效**。

**修法**：旧 origin 必须取自**前端实际的 `location.origin`**，并由服务端独立严格校验
（**不能直接信任 body 里的字符串**）。

### ✅ 已冻结的最终实现要求（改这块前先读，不要自行简化）

```
/healthz 响应：{"service":"wbapi","ready":true,"restartId":"<本次重启标识>"}

CORS（只作用于 /healthz，不扩到 /api/panel-token 及其它 /api）：
  白名单 = {本次重启的旧 origin, 本次重启的新 origin}   ← 每次重启重建，不累积历次旧 origin
  旧 origin 来源：前端 location.origin，服务端独立严格校验
  严格校验：协议/主机(回环)/端口，不用前缀匹配；拒绝 null、伪装域名、非回环
  头：回显精确 origin + Vary: Origin + Cache-Control: no-store；不用 *、不用 credentials

导航四条件（缺一不导航）：
  response.ok && service==='wbapi' && ready===true && restartId===本次标识

restartId：crypto/rand 固定长度 hex；不进配置/URL/日志/usage；
           子进程用参数数组启动（不拼命令行）；缺失/错格式/不匹配 → 握手失败；
           每次重启新值不复用；断言 202 值 == 传给子进程的值 == 健康响应里的值

旧 origin 为何可保留到子进程退出（**理由要记对，别用错理由**）：
  是"健康响应只含就绪状态与交接标识、不授予写权限"，
  **不是**"旧端口已停止监听所以没有暴露面" ——
  已加载的页面仍保留原 origin、仍能发请求；旧端口以后也可能被别的程序占用。
```

### 验收 6 场景（Codex 定稿，不新增）

| # | 场景 | 期望 |
|---|---|---|
| 1 | 新服务返回 503 | 不导航，继续等待 |
| 2a | 无关服务 200 + 通配 CORS | 不导航 |
| 2b | 200 + 正确 CORS + service 正确 + ready:true + **restartId 错误** | 不导航 |
| 3 | 旧 origin 探测新 origin（含 **`localhost`** 旧 origin） | 能读到 body（显式断言） |
| 4 | 实际改端口重启 | 面板**自行导航**，新页面能保存设置 |
| 5 | 新端口被占用 | 旧服务恢复，**有限时间内**显示失败，不无限轮询 |

### 🔴 两条方法论教训（比单个 bug 更值得记）

1. **场景 4 必须由面板自行导航，测试脚本不得代它跳转。**
   测试脚本代跳 = **绕过被测的生产逻辑**（导航决策恰恰是要验的东西），
   会得到"全绿但生产是坏的"。这是 Codex 第 19 轮明确强调的。
2. **这 4 个缺陷 Go 单测和前端自测全都抓不到**，只有真实浏览器跨 origin 才暴露 ——
   与第 17 轮 CDP 抓到的"前后端契约不一致"同型。
   **凡涉及浏览器安全模型（CORS/Origin/opaque）的判断，一律用真实浏览器实验定性，
   不要靠推理** —— 我这次 4 条里有 2 条推理是错的（坑 2 的"type 会接住"、坑 4 的"监听地址即 origin"）。

## 六之四、🔴 实现阶段的三个坑（2026-10-05，写验收脚本时踩到）

### 坑 A：`--addr` 与配置 `port` 在**启动**和**重启**两条路径上口径不一致

- **启动**（`serve.go`）：`flag 优先，其次配置` → `--addr 127.0.0.1:8891` 时监听 8891。
- **重启**（`restart.go` 的 `plannedListenAddr`）：**只读配置的 port**，不看 `--addr`。

所以 `wbapi serve --addr 127.0.0.1:8891`（而配置里 `port: 8787`）时，
点一次重启会**跳到 8787**，而不是留在 8891。

**影响面（已评估，决定暂不改）**：
- **正常用户不受影响**：面板改端口会走 PATCH 写配置，`--addr` 与配置一致。
- **只有"手工用 `--addr` 指定了与配置不同的端口"这一种情况会意外跳端口**。
- 写验收脚本时**极易踩到**：脚本为了隔离用 `--addr <临时端口>` 起服务，
  若没同步把配置 PATCH 成同一端口，重启就会跳到默认 8787，
  测试现象是"面板导航到了别的端口"，很容易误判成导航逻辑有 bug。

**验收脚本的正确做法**（现有脚本已这样做）：起服务后先
`PATCH /api/settings {port: NEW_PORT}`，让配置与目标端口一致，再触发重启。

**若将来要统一口径**：让 `plannedListenAddr` 也考虑"进程实际监听的地址"，
或启动时就禁止 `--addr` 与配置不一致。**本次不做** ——
它会改变既有启动语义，收益（只影响手工用法）小于风险。

### 坑 B：CDP 合成鼠标点击必须带 `mouseMoved` 与 `buttons`

`Input.dispatchMouseEvent` 只发 `mousePressed`/`mouseReleased` **不产生 click**。
必须：`mouseMoved` → `mousePressed{buttons:1}` → `mouseReleased{buttons:0}`。
（我第一版漏了，点击静默失效。逐项反向对照确认这是必要条件之一。）

### 坑 C：`st-restart-msg` 是"自我擦除"的信号，不能当成功判据

重启失败的 catch 分支会把 `st-restart-msg` 清回空串（`settings.js` 的 catch）。
所以在**失败的**路径上，这个元素最终**永远是空的** ——
用"它是否为空"判断"handler 有没有跑"，会得到**假阴性**。
正确的观测点是：MutationObserver 抓瞬时写入、或 `#st-confirm-ok` 的 `disabled` 翻转、
或直接看 `fetch` 调用记录。

> ⚠️ 我据"msg 为空"一度判断"点击没生效"，**那是测量假象**；
> 更可靠的信号是 `fetch` 探针（它记录到了 `POST /api/settings/restart`）。
